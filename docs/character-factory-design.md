# SD 인간형·사족보행 캐릭터 공장 분석과 설계

2026-09-18 선행 명세: [AI 캐릭터 파츠 이미지 공장 v1](ai-character-parts-image-factory-spec.md). 새 파츠의 이미지 생산 계약은 이 독립 명세를 기준으로 하며, 3D 생성·피팅 완료와 구별한다.

후속 구현: 사용자가 메이플풍 SD 캐릭터·무기·장비와 GPT Image 2.5로 범위를 구체화했다. 현재 추가된 기능과 검증은 [메이플 캐릭터 생산](maple-character-pipeline.md)을 따른다. 아래 내용은 그 이전 분석 기준이다.

## 결론과 범위

현재 저장소는 **인간형 캐릭터 작업 제어와 공통 리그 조립의 기반**을 갖췄다. 몸·옷의 형태와 변형 품질이 보장되는 양산 공장, 사족보행 자동 리깅 공장은 아직 아니다.

목표는 메이플풍의 큰 머리·짧은 팔다리를 가진 독자 SD 캐릭터를 공통 몸 위에서 조합하고, 사족보행은 별도 몸·리그 규격으로 생산하는 것이다. 공통화할 대상은 작업 일지·원본 추적·검수·배치 관리다. 인간형과 사족보행의 골격과 가중치는 각각 설계한다.

사용자가 우선순위를 확정하기 전의 제안 순서: SD 인간형 한 몸 규격과 교체 의상 → 반복 생산·검수 → 사족보행 한 체형 → 체형 확장. 이는 구현 설계이며 새 기능이 이미 존재한다는 뜻이 아니다.

분석 기준: 2026-09-16, HEAD `1908dbd`와 현재 미커밋 변경, 첨부된 전체 코드 분석. 주요 API·작업 서비스·기하 조립·리그·런타임 계약을 검토하고 아래 검사를 실행했다. 모든 분기, 유료 제공자, 운영 DB를 검증하지는 않았다. 기존 변경 및 문서 삭제 7개는 보존했다. 삭제된 제어·준비 계약은 HEAD에서 읽었다.

## 1. 현재 기반과 확장 경계

| 영역 | 확인한 구현 | 공장을 위해 필요한 작업 |
|---|---|---|
| 입력/제어 | `character_pipeline.py`: 업로드, 해시, 소유권, revision, operation | 몸 유형·규격·제작 방식의 명시적인 선택 |
| 제공자 | `character_jobs.py`: 생성, 리깅, 제출 의도, task 복구, 다운로드 | 종류별 지원 여부와 생산 계획의 연결 |
| 기존 모델 분리 | `character_segmentation.py`, `character_parts.py`: 원본 면 선택과 버전 출력 | 의미 검수, 피부 누락 범위, 원본 리그 보존 검수 |
| 이미지 생산 | `avatar_blueprints.py`, `avatar_image_pipeline.py`: 8개 레이어, 개별 파츠 생성, 재개 | 몸 규격과 일치하는 시안, 파츠별 제작 규칙 |
| 리그 조립 | `avatar_factory_geometry.py`: 몸 생성, 박스 맞춤, 거리 기반 가중치 | 표준 몸에 맞춘 피팅과 의상 유형별 스키닝 |
| Blender | `avatar_factory_blender.py`: 조립, 렌더, GLB/BLEND, 완료 영수증 | 체형별 골격·변형 검수·동작 세트 |
| 옷장 | `frontend/src/avatar/`: 공통 skeleton, 장착·마스크·동작·복원 | 프로필별 리그, 분리된 파츠 슬롯, 승인 카탈로그 |
| 작업 기반 | 캐릭터/공장/월드에 서로 다른 작업 관리 | 공통 수락·복구 계약, 단계별 executor 어댑터 |
| 검수 | 캐릭터 검수와 공장 `review_required` | 공장 출력 버전에 묶인 승인/수정 요청, 출시 목록 |

기존 `/api/world/*`, CLI, manifest v1과 두 인간형 rig ID는 호환 경로로 유지한다. 공장 확장을 이유로 전체 프레임워크를 교체할 필요는 없다.

## 3. 추가로 확인한 생산 품질 문제

### 3.1 비율 규격이 일치하지 않는다

`avatar_blueprints.PROMPT`는 약 2.5등신을 지시한다. `avatar_factory.IMAGE_PROFILE`의 `maple-chibi-v3`는 키 1.81, 머리 높이 1.14, 약 1.59등신이다. 원본 GLB용 `PROFILE`은 약 2.45등신이다. 서로 다른 프로필 자체는 가능하지만 생성 시안·접합점·리깅·UI가 선택한 규격 하나에서 나와야 한다.

조치: 버전이 있는 `BodyProfile`에서 비율, 축, 랜드마크, 파츠 접합점, rig ID, 동작 규격을 읽는다. 최초 제품의 등신 비율은 정면·측면·걷기 시안을 보고 확정한다. 숫자만 맞추어 시각 승인을 대신하지 않는다.

### 3.2 옷의 종류와 가중치가 분리되지 않았다

`part_weights()`는 최신 SD 경로에서 `bottom` 전체를 `hips`에 연결한다. 치마가 양다리로 찢어지는 것을 피하는 규칙이지만 바지도 같은 규칙을 받는다. 바지가 무릎을 따라 변형되는 계약이 없다. `ROLE_SLOT`도 바지·치마를 `bottom`으로 합친다.

조치: 슬롯과 제작 유형을 구별한다. 같은 하의 슬롯이라도 `pants`, `shorts`, `skirt`는 서로 다른 가중치·가림 범위·검사 자세를 사용한다. 바지는 좌우 다리 체인, 치마는 골반과 필요 시 추가 변형 뼈를 사용한다. 치마 물리 시뮬레이션은 별도 범위다.

### 3.3 파츠 변환은 표준 몸에 대한 실제 피팅이 아니다

`compile_part_models()`는 파츠 경계 상자를 고정 `PART_BOXES`/`MAPLE_BOXES`에 맞추며 축별 크기를 조정한다. 가중치는 `weights_for()`의 뼈 선분 거리에서 계산한다. 표준 몸 표면을 따라 옷을 맞추거나 몸의 가중치를 전달하는 알고리즘은 아니다.

조치: 의상 생성 입력에 몸 규격과 전후좌우 참고를 포함한다. 랜드마크 정렬 → 몸에 대한 여유 간격을 둔 피팅 → 몸/검증된 의상에서 가중치 전달 → 변형 검사 순으로 구현한다. 전이 방식은 `canonical_rebind`로 남기고 원본 가중치 보존으로 표시하지 않는다. 무조건 shrinkwrap하면 장식·소매·치마 실루엣이 무너질 수 있으므로 영역별 규칙이 필요하다.

### 3.4 이미지 파츠 구분이 런타임까지 유지되지 않는다

생성 시 `hairBack`, `hairFront`를 분리하지만 최종 패키지는 `hair`로 합친다. 현재 옷장에서는 앞·뒷머리를 독립 교체할 수 없다. 좌우 신발도 한 생성 슬롯이다. UI의 레이어 수와 최종 교체 가능한 파츠 수를 구분해야 한다.

조치: 앞·뒷머리의 독립 장착을 manifest 차기 버전에 도입하고 구버전 `hair`는 통합 헤어로 유지한다. 신발은 한 쌍 상품이어도 좌우 메시·가중치 검사 결과를 개별 기록한다.

### 3.5 가림 마스크와 완전한 몸은 별개다

`MASKS`는 슬롯별 고정 몸 영역을 숨긴다. 반팔·긴팔·반바지·긴바지의 덮는 영역은 서로 다르므로 슬롯 이름만으로 결정하면 구멍 또는 관통이 생길 수 있다. 기존 공통 몸은 티셔츠·반바지 형태가 포함된 제작 템플릿이다.

조치: 피부/베이스 몸과 교체 가능한 기본복을 구별한다. 각 의상 버전에 실제 coverage를 저장한다. 기존 옷 입은 캐릭터에서 숨겨진 몸이 존재하지 않으면 `missing`/`unknown`으로 기록하고 몸 제작 단계로 넘긴다. 분리만으로 몸이 복원되었다고 표시하지 않는다.

### 3.6 인간형 계약이 여러 층에 고정되어 있다

공장 검증은 23본·7개 동작을 전제한다. Blender 변형 렌더는 팔·다리 이름을 직접 사용한다. 프론트 `types.ts`, `manifest.ts`, `skeleton.ts`는 인간형 본 목록과 두 rig ID를 사용한다. 사족보행 JSON 하나를 추가해도 현재 런타임에서 동작하지 않는다.

조치: 리그 프로필이 본 계층·rest transform·socket·필수 동작·검사 자세를 소유하게 한다. 작업 UI는 프로필별 capability를 사용한다. 지원하지 않는 rig ID는 명시적으로 거절한다.

## 4. 생산 라인 세 가지

### A. 표준 몸 기반 SD 인간형 — 양산의 주 경로

1. 승인된 표준 몸과 리그 선택.
2. 얼굴/앞머리/뒷머리/모자/상의/하의/신발/장신구 시안 제작.
3. 시안의 비율·정체성·뒷면·옷의 입구 검수.
4. 파츠별 3D 생성 또는 직접 제작 모델 가져오기.
5. 표준 몸의 목·어깨·허리·손목·발목에 맞춤.
6. 변형 의상은 공통 리그에 가중치 연결, 단단한 소품은 bone/socket 장착.
7. 몸 가림 범위·의상 충돌·필요 파츠 정의.
8. GLB/BLEND, 정면·측면·후면 및 동작 검사 출력.
9. 버전별 시각 승인 후 카탈로그 공개.

모든 옷에 Meshy 리깅을 따로 요청할 필요는 없다. 이미 승인된 몸의 골격을 공유해야 교체할 때 동작이 유지된다. 몸은 최초 제작·승인 비용을 들이고 재사용하며, 의상만 추가 생산한다.

### B. 기존 리깅 모델의 보존 분리 — 가져오기 경로

1. 원본 GLB와 provenance, SHA-256 등록.
2. skeleton, skin, animation, 면 선택 가능 여부 검사.
3. 원본 해시에 묶인 node/primitive/face 선택으로 몸·옷·헤어 분리.
4. 원본 JOINTS/WEIGHTS와 inverse bind, 애니메이션 연결 보존 검사.
5. 몸 누락 범위를 기록하고 새 GLB/BLEND 버전 출력.

이 경로의 성공은 공통 SD 옷장 호환을 자동 보장하지 않는다. 다른 리그를 공통 리그로 옮기려면 별도 변환 버전과 검수가 필요하다.

### C. 사족보행 — 별도 리그 경로

공식 [Meshy Rigging API](https://docs.meshy.ai/en/api/rigging)는 표준 인간형 중심이며 non-humanoid를 자동 리깅 부적합 대상으로 명시한다. `character_jobs.py`도 사족보행 API 리깅을 차단한다. 웹앱 기능이 API에 동일하게 제공된다고 가정하지 않는다. 생성 모델 선택은 현재 [Image to 3D 계약](https://docs.meshy.ai/en/api/image-to-3d)에 따라 Meshy 7 또는 Smart Topology `meshy-t2`를 사용한다. 분리된 출력이 의상 의미·숨겨진 몸을 보장하지는 않는다.

초기 사족보행은 개/고양이와 유사한 **한 가지 체형**으로 제한한다. 말·곰·거미까지 한 리그의 단순 스케일 변형으로 다루지 않는다.

제안 공정:

1. 4개 다리가 구분되는 중립 자세의 모델과 체형 프로필 선택.
2. 어깨·골반·앞뒤 무릎/관절·발·목·꼬리 랜드마크 배치 및 검수.
3. 전용 Blender worker에서 본 생성, 가중치 계산, 필요 부분 수정.
4. 제작용 IK/FK 제어 리그와 게임용 deform skeleton을 구별하고 동작을 bake.
5. idle/walk/run/turn 검사: 네 발 접지, 미끄러짐, 척추·목·꼬리 변형 확인.
6. 본체·안장·목걸이·모자·갑옷 파츠 장착 검사 후 내보내기.

이미 리깅된 사족보행은 가져오기 경로로 수용할 수 있도록 설계한다. 신규 로컬 리깅은 `local_authored`, 제공자 실패 뒤 대체 리깅은 `local_fallback`, 불명확한 가져오기는 `unknown`으로 구별한다. 이 worker와 사족보행 런타임은 현재 미구현이다.

## 5. 공통 데이터·실행 계약 제안

신규 개념은 다음과 같이 작게 나눈다. 아래 필드·API는 설계안이며 기존 스키마가 아니다.

| 객체 | 소유할 정보 |
|---|---|
| BodyProfile | ID/버전, bodyType, 비율/랜드마크, rigProfile, 기본 몸 asset hash |
| RigProfile | 본 계층/rest transform, deform 본 목록, sockets, 요구 동작, 검사 자세 |
| PartRecipe | slot, garmentType, 기준 몸, source hash, fit/bind 방식, coverage, conflicts |
| ProductionPlan | owner, 입력 snapshot, 프로필 버전, 단계 의존성, 제공자별 시도 상한 |
| StageReceipt | 단계 ID, 입력/출력 hash, 시도 상태, provider task ID, executor 증거 |
| Review | output version/hash, 기술/변형/시각 판정, evidence IDs, 검토자, 시각 |

`planned → accepted → running → review_required → approved`를 기본 흐름으로 두고 `failed`, `recovery_required`, `changes_requested`를 명시한다. 제공자 상태는 단계 상태와 따로 보존한다. 출력 또는 레시피가 바뀌면 새 버전을 만들고 이전 승인을 승계하지 않는다.

운영 규칙:

- owner + idempotency key + 입력 fingerprint로 수락 기록을 응답 전에 저장한다.
- 같은 요청은 동일 작업을 반환하고 다른 입력은 409로 거절한다.
- CLI/API는 같은 단계 잠금과 실행기를 사용한다. 현재 단일 worker 제약을 유지한다.
- 유료 POST 전 시도 기록을 남긴다. 응답 유실은 task ID 복구로 처리한다.
- 파츠 한 개만 실패하면 그 파츠 이후의 의존 단계만 무효화한다. 승인된 몸과 다른 파츠는 재생성하지 않는다.
- 로컬 rebuild에는 provider 제출이 없는 실행 계획을 사용한다.
- DB는 조회 인덱스로 유지한다. 이 설계 적용에 DB schema 변경을 전제하지 않는다.
- 미구현 stage는 실행 가능 action으로 노출하지 않는다.

예상 API 확장: 기존 공장 router에 프로필 조회, 생산 계획 미리보기, 버전 검수 저장을 추가한다. 검수 요청은 owner·revision·artifact hash와 서버에 등록된 evidence ID를 검사한다. 기존 생성·rebuild URL은 유지한다. 배치 실행은 이 단계별 서비스를 호출하며 별도의 provider 제출 로직을 만들지 않는다.

## 6. 브라우저 공장 화면

`생산 목록 → 몸 규격 → 파츠 제작 → 피팅/리깅 → 동작 검수 → 승인 카탈로그`의 흐름으로 구성한다.

- 생산 목록: 입력, 인간형/사족보행, 현재 단계, 실패 이유, 저장된 task ID, 재개 가능 여부.
- 몸 규격: 정면/측면, 비율, 기준 리그와 사용 가능한 파츠. 미구현 사족보행 생성은 활성화하지 않는다.
- 파츠: 몸만/옷만/전체 보기, 앞·뒷머리, 의상 종류, 관통·누락 범위 표시.
- 리깅: 본 표시, 랜드마크, 가중치 검사와 좌우 대칭 확인.
- 동작: 프로필별 필수 동작 재생, feet contact와 의상 관통 검수.
- 검수: 기술 통과와 시각 승인을 별도 표시. 검토한 출력 버전에 대해 승인/수정 요청 저장.
- 복구: 새로고침 시 서버 상태를 불러오고 응답 유실 시 같은 수락 기록을 복구.

R3F가 scene 수명을 소유하고 WebGPU/호환 모드를 구분한다. gaesup-world와 기존 장착·자원 해제 구조를 유지한다. 코드명·provider 내부 설정은 제작 판단에 필요한 경우에만 화면에 표시한다.

## 7. 구현 순서와 통과 기준

| 단계 | 주 수정 위치 | 완료 기준 |
|---|---|---|
| 0. 수락·저장 신뢰성 | `world.py`, `ImageWorkbench.tsx`, 관련 테스트 | 동일/다른 사용자와 동시 요청에서 제출 1회, 다른 입력 409, 지연 저장이 다른 편집을 덮지 않음 |
| 1. 몸/리그 프로필 | 새 프로필 서비스, `avatar_blueprints.py`, factory·runtime | 생성 시안·접합점·리그가 동일 버전, 기존 두 인간형 규격 호환 |
| 2. SD 의상 생산 | geometry/Blender, manifest·assembler | 바지/치마 구분, 앞뒤 헤어 교체, 몸과 옷의 분리, 정면·후면·걷기 품질 |
| 3. 검수·반복 생산 | factory API/service, Factory UI | 출력 hash에 묶인 승인, 수정은 새 버전, 승인 카탈로그 구분 |
| 4. 사족보행 한 체형 | 전용 Blender worker, rig profile, runtime | 네 다리·목·꼬리의 실제 리깅, 지정 동작 bake, GLB 재가져오기 및 화면 재생 |
| 5. 배치 운영 | production plan·stage receipt와 대시보드 | 재시작·단계 실패 시 중복 비용 없이 재개, 부분 재생산, 비용/실패/품질 측정 |

최초 양산 통과 표본 제안: 승인 몸 1개, 다른 상의 2개, 바지 1개, 치마 1개, 헤어·모자·신발을 조합해 옷 교체와 동작을 확인한다. 이어 사족보행 1개에 목걸이/안장 등 파츠를 장착한다. 이는 실행하거나 승인받은 유료 배치가 아니다.

성능은 폴리곤/텍스처/재질 수와 draw call, 로딩 시간, 메모리, 장착 교체 시간을 실제 대상 장치에서 측정해 예산을 정한다. 지금의 큰 공유 번들만으로 병목 또는 개선 효과를 단정하지 않는다.

## 8. 이번 실행 검증

| 검사 | 결과 | 증거의 범위 |
|---|---|---|
| 루트 `uv run pytest -q` | 137 통과, deprecation 경고 2개 | 현재 작업 트리의 테스트. 외부 호출/DB 대체가 포함됨 |
| frontend `npm run build` | 통과 | 타입 검사 및 빌드. 공유 청크 3,884.30 kB/gzip 1,295.99 kB 경고 |
| frontend `npm run test:e2e`, API 포트 18012 | 10 통과, 54.9초 | 임시 데이터·빈 provider 설정. 실제 로컬 API, 복원, 오류, Blender 면 분리 포함 |
| backend `uv run python tests/run_avatar_factory_check.py` | 통과 | 실제 Blender, fixture 파츠 6개, 23본·7개 동작, GLB/BLEND·렌더 출력 |

공장 fixture의 `rest.png`를 직접 확인했다. 둥근 분절 몸과 의상·헤어·모자가 조립된 테스트 캐릭터다. 이 결과는 실제 Meshy 캐릭터의 형태나 판매/게임용 시각 품질을 승인하는 증거가 아니다. 해당 fixture는 `rig-v1`/기존 SD 프로필을 사용하므로 최신 `maple-chibi-v3`의 품질 검증으로 확대하지 않는다.

브라우저 검사는 WebGPU 또는 WebGL 호환 경로를 허용한다. 이번 결과만으로 WebGPU 전용 통과를 선언하지 않는다. 일부 fixture에서 normal attribute 및 초기화 방식 경고가 있었으나 테스트는 통과했다.

이번 변경은 이 분석·설계 문서 추가다. 기존 코드 문제 수정, 새 파이프라인 구현, 사족보행 리깅, 유료 생성, 실제 캐릭터 품질 승인, 운영 PostgreSQL·배포는 수행하지 않았다.
